# Offline RL Dataset and OPE Protocol

## Scope

The offline RL dataset is generated by `DynamicSimulator` v2. It is useful for testing collection, learning, and estimator implementations, but it is **not real driver trajectory data** and cannot establish real-world policy value.

NYC TLC records do not contain logged recommendations, driver acceptance decisions, or behavior-policy propensities. Therefore IPS, WIS, and doubly robust OPE are not identifiable from TLC trips alone.

## Trajectory generation

Each simulator decision records:

```text
(state before decision, action zone, net reward, next state, done,
 driver/episode trajectory ID, decision timestamp, behavior probability)
```

A trajectory belongs to one driver in one simulation episode. Its ID is stable and unique within a collection run, transitions are stored in time order, and its final transition has `done=True`. This matters because OPE resamples and evaluates complete trajectories rather than unordered transitions.

A strategy can return either:

```python
action_zone
# or
(action_zone, probability_of_that_action_under_behavior_policy)
```

Returning only an action is retained for compatibility and records probability `1.0`; this is appropriate only for a genuinely deterministic behavior policy.

## State and action

The seven-dimensional state is:

| Index | Feature |
|---:|---|
| 0 | zone ID / 263 |
| 1 | minute of day / 1440 |
| 2 | local supply / total taxis |
| 3 | effective demand / 200, clipped at 1 |
| 4 | pickup probability |
| 5 | local supply / remaining trips |
| 6 | traffic multiplier / 2 |

The action is a target taxi-zone ID in `1..263`. Staying means selecting the driver's current zone; it is not tied to one fixed zone.

## Reward

For a successful pickup:

```text
reward = fare - fuel cost - travel-time cost
         - competition penalty - risk penalty
```

A failed pickup currently produces zero transition reward. The simulator's aggregate metrics separately report revenue and penalty components.

## Required OPE inputs

Trajectory-aware WIS requires, for every logged transition:

- trajectory ID and terminal boundary;
- behavior-policy probability `mu(a_t | s_t)` in `(0, 1]`;
- target-policy probability `pi(a_t | s_t)` in `[0, 1]`.

Sequential DR additionally requires nuisance predictions:

- `Q(s_t, a_t)` for the logged action;
- `V^pi(s_t)`;
- `V^pi(s_{t+1})`.

The implementation uses cumulative ratios `pi/mu`, per-decision self-normalized WIS, sequential DR contributions, and complete-trajectory bootstrap confidence intervals. Missing probabilities or nuisance predictions are errors rather than silently assumed values.

`ope_fqe` is intentionally labeled a diagnostic when it bootstraps with logged next actions. It is not by itself a target-policy value estimate without target-policy next actions or values.

## Reproducible benchmark

```bash
python -m scripts.run_ope_comparison --drivers 10 --seed 42
```

The benchmark reports its seed, behavior and target policy definitions, transition and trajectory counts, estimator-specific intervals, and overlap limitations. The IQL benchmark uses uniform random behavior with probability `1/263` and a deterministic greedy target policy.

## Known limitations

1. Simulator calibration and reward misspecification can dominate estimator error.
2. The state is only a partial market observation.
3. Deterministic targets can have poor overlap with exploratory behavior data; bootstrap intervals do not fix missing support.
4. Drivers do not strategically adapt within the current simulator.
5. Ring-buffer truncation can remove the beginning of a trajectory. OPE consumers must use `as_ordered_dict()` and retain only complete trajectories when capacity is insufficient.

Real-world OPE claims require a deployed logging policy that records recommendations, accepted actions, propensities, timestamps, outcomes, and episode boundaries.
